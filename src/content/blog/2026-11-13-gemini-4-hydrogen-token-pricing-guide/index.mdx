## 🧠 3. 【最重要】思考（Thinking）機能とトークン消費のメカニズム

モデルが内部で自問自答し、推論ステップを組み立てる「Thinkingプロセス」で生成されたトークンは、**すべて出力トークン（$7.50 / 1M tokens）としてカウント・請求**されます。

## ⚠️ 4. 3.8 Flashからの移行で起きる「トークン消費量・コスト急増の罠」

ここが実戦における最大の落とし穴です。

### デフォルト値の引き上げ（medium ➔ high）
前身である **Gemini 3.8 Flash のデフォルト Thinking Level は `medium`** でした。
しかし、**Gemini 4 Hydrogen ではデフォルトが `high` に引き上げられました！**

### 何が起きるのか？
これまでGemini 3.8 Flashで動かしていたエージェントスクリプトを、単にモデルIDだけ `gemini-4-hydrogen` に差し替えた場合：

1. パラメータ無指定だと、すべての呼び出しで自動的に `high` 思考が発動する。
2. 1回のリクエストあたり、思考トークンが従来の2倍〜4倍（2,000〜4,000トークン）消費される。
3. エージェントが10回ツールを実行した場合、**思考トークンだけで20,000〜40,000トークン（約$0.15〜$0.30）が上乗せ**される！
4. 「前より速くなったけれど、API利用料の減りが異常に早い…」という事態に陥る。

### 解決策：Thinking Levelをタスクに応じて明示指定する
Python SDK等で呼び出す際は、タスクの性質に応じてThinking Levelを明示的に指定することが不可欠です。

```python
from google import genai
from google.genai import types

client = genai.Client()

# 高速・低コストにツール呼び出しやルーティンを回す場合
config = types.GenerateContentConfig(
    thinking_config=types.ThinkingConfig(
        thinking_level="low"  # または "medium" を明示してトークン浪費を防ぐ
    )
)

response = client.models.generate_content(
    model="gemini-4-hydrogen",
    contents="以下のJSONデータからエラーログのみを抽出してください: ...",
    config=config
)

# 実際のトークン消費量を確認する
print(f"入力トークン: {response.usage_metadata.prompt_token_count}")
print(f"思考トークン: {response.usage_metadata.candidates_token_count}")
```

## ⚙️ 5. サンプリングパラメータ（temperature等）の無視仕様

もうひとつの重要な仕様変更として、推論モデル特有の**「サンプリングパラメータ無効化」**があります。

APIリクエストで `temperature`、`top_p`、`top_k` を指定しても**エラーにはなりませんが、サーバー側で完全に無視され、モデル固有の最適分布でサンプリングされます**。

「temperatureを0にして完全固定の出力を得る」といった従来のプロンプトテクニックは通用しないため、決定論的な結果が欲しい場合は、プロンプト内で明示的に制約を与えるか、Structured Outputs（スキーマ強制）を利用してください。

## 💡 6. トークン消費量を極限まで抑える3大ベストプラクティス

Gemini 4 Hydrogenを最大限コストパフォーマンス良く運用するための実践ルールです。

### ① 暗黙的キャッシュ（95%割引）を狙い撃ちするプロンプト設計
Hydrogenでは、**先頭のコンテキストが一致していれば、自動的に暗黙キャッシュが適用**されます。
- システム指示（System Instruction）や共通ルール（コーディング規約等）は、必ず**プロンプトの最先頭に固定**する。
- 毎回変わる可変データ（ユーザー入力や動的ファイル）は末尾に配置する。
- これにより、2回目以降の入力トークンコストが **$1.50 ➔ $0.075（約1/20）** に激減します。

### ② エージェントループ内の思考レベル動的コントロール
- ファイル検索やコマンド実行などの「単純な道具使いターン」: `thinking_level: "low"`
- 複雑なエラー原因の特定やアーキテクチャ設計ターン: `thinking_level: "high"` または `"xhigh"`
- タスクに応じてレベルを切り替えることで、全体のトークン消費量を60%以上削減可能です。

### ③ 夜間バッチや非リアルタイム処理はBatch API（50%オフ）を活用
即時性が求められないテスト自動生成や静的コード解析は、Batch APIを使うことで入力$0.75 / 出力$3.75（半額）で実行できます。
